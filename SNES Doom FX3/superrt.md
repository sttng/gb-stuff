I've gone through the SuperRT code and checked it against the sd2snes mk3. **It can't be ported as it stands.** The design is roughly 4× too big for the EP4CE15 in multipliers, logic and block RAM, even with only one of its three execution units. The memory problem is easy to fix on the sd2snes. The arithmetic problem means redesigning the ray-tracing core, and the result would run at a fraction of the original speed.

### How I measured it

Quartus doesn't run here, so I converted the sources to plain Verilog and ran them through Yosys, an open-source synthesis tool. That gives a count of every multiplier with its real operand widths, plus logic and flip-flop counts with the multipliers taken out. I ran it twice: with all three execution units, and with units 1 and 2 turned off in `Config.sv`. Treat the numbers as estimates.

| Resource                                | SuperRT, 3 units (as shipped)    | SuperRT, 1 unit                 | EP4CE15F17C8            |
|-----------------------------------------|----------------------------------|---------------------------------|-------------------------|
| Multiplies (in 18×18 multiplier blocks) | 259 multiplies, about 650 blocks | 95 multiplies, about 234 blocks | **56**                  |
| Logic, not counting multipliers         | about 27K LUT4 + 27K flip-flops  | about 10K LUT4 + 10K flip-flops | **15,408 LEs** in total |
| Block RAM                               | about 1.9 Mbit (about 240 M9K)   | about 1.8 Mbit                  | **504 Kbit (56 M9K)**   |

The original runs on a DE10-Nano (Cyclone V 5CSEBA6, about 42K ALMs, 112 DSP blocks, about 5.5 Mbit of RAM). It already needs that whole chip: the README says it won't fit with all three units plus the debug display.

### Block RAM: solvable

Almost all of it goes on four buffers:

- **Program ROM:** 64 KB.
- **RGB555 framebuffer:** 64 KB (200×160 pixels × 2 bytes).
- **Two converted frames for the SNES:** 32 KB each.
- **Palette map:** 32 KB.

On the mk3, the program ROM moves to the cartridge PSRAM like any other ROM. The demo doesn't use the 512 KB SRAM, so it can hold the framebuffers. That puts the whole framebuffer pipeline on its own memory bus. Per rendered frame it moves about 200 KB, which is a few milliseconds of SRAM time even at a conservative 20 MB/s. The palette map can be appended to the ROM image and read from PSRAM.

What stays on-chip is the 4 KB command buffer per unit, the branch-prediction RAM and the usual sd2snes buffers. That's about 10–20 M9K.

### Multipliers and logic: the real blocker

All the maths is 18.14 fixed point. The execution pipeline does an intersection test every clock with everything fully parallel. Per unit, that's about 123 blocks in the execution engine, 28 each in the reciprocal and square-root units, and 27 in colour and secondary-ray maths. Even after Yosys trimmed unused bit widths, many multiplies are still 32×32, which costs 4 blocks each on a Cyclone IV.

A single unit is still about 4× over the 56 blocks. Its pipeline registers alone are about 10K flip-flops, before adding the sd2snes infrastructure (MCU/SPI, SD DMA, PSRAM/SRAM control). Timing is also a problem: the reciprocal and square-root code chains three 32×32 multiplies in one clock, which a C8 part won't close at a useful speed.

Making it fit means rebuilding the execution unit:

- Share a small set of pipelined multipliers across several clocks per operation, instead of one per operation per clock.
- Let sphere, plane and box tests share one set of multipliers, since each instruction is only one type.
- Replace the two-step Newton reciprocal and square root with a block-RAM seed table plus one step.
- Share 1–2 multipliers for the per-pixel colour maths. It runs once per pixel, so speed barely matters there.

### Expected performance

The original does up to about 150M intersection tests per second (3 units × 50M) and gets about 20 fps on the demo scene. A redesigned single unit at the sd2snes's 86 MHz, taking about 4 clocks per test, would do about 21M per second. That's **roughly 2–4 fps on the same scene**; lowering the resolution would help in proportion.

### What carries over easily

- **The SNES interface gets simpler.** The sd2snes sees the real address bus and both read and write strobes. All of SuperRT's level-shifter workarounds and 8-sample glitch filtering go away. Writes can stay emulated as reads from `$BF00–$BFFF`, so `SRTTest.sfc` runs unchanged.
- **The renderer control and the PPU converter** port mostly as-is.
- **Selecting the core:** the firmware needs to recognise the ROM and load a dedicated `fpga_srt.bi3`, the same pattern as your Xeno Crisis core.
- **Build prerequisites:** `PaletteMap.bin` and `SRTTest.sfc` aren't in the repo. They're generated by the Windows-only C# testbed (SharpDX) plus wla-dx and a patched libSFX, so that has to happen first. The testbed's cycle-accurate model is handy as a reference, but a redesigned core won't match it cycle for cycle, so you'd compare finished pixels.

### Suggested route

1. **Infrastructure core first** (`sd2snes_srt`): the sd2snes base plus SuperRT's register file, framebuffers in SRAM, and a test-pattern stand-in for the renderer. This proves the SNES side end to end and is moderate work.
2. **The redesigned execution unit:** the bulk of the effort.

A cheap check before committing: retarget `SRT.qsf` to EP4CE15F17C8 with one unit enabled and let Quartus's synthesis report confirm these numbers. It won't fit, but the report is the authoritative resource count.
